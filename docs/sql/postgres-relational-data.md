# Загрузка данных в новую схему

Приватные файлы создаёт команда:

```sh
python3 scripts/export_relational.py
```

- `data/postgres-relational-data.sql` — данные для новой реляционной схемы.
- `data/postgres-relational-data.manifest.json` — контрольные суммы, количество записей, сверка сумм.
- `data/postgres-relational-data.report.md` — читаемый отчёт и вопросы к исходным данным.

Файлы содержат финансовую информацию; SQL включает хеши паролей существующих
пользователей. Они создаются с правами 0600 и исключены из Git. Исходные JSON,
SQLite вместе с WAL и исходные Excel нужно сохранить отдельно.

## Порядок в DBeaver

1. Используйте базу, в которой успешно выполнен `postgres-relational-schema.sql`.
2. Откройте отчёт переноса. Затем откройте **новый** файл `data/postgres-relational-data.sql`.
3. Выполните весь файл от BEGIN до COMMIT как один скрипт.
4. При ошибке выполните `ROLLBACK;` и сохраните текст ошибки. Не запускайте отдельные INSERT вручную.
5. После успеха обновите список таблиц и выполните запросы ниже.

Файл рассчитан на пустую новую схему с первоначальными служебными записями.
Он не удаляет данные и отказывается работать при повторном запуске или
обнаружении пользовательских записей. Старые `postgres-data.sql` и
`postgres-data-parts` не используются.

```sql
SELECT status, summary FROM qarzhy.import_batches;
SELECT code, count(*) FROM qarzhy.import_issues WHERE status='open' GROUP BY code ORDER BY code;
SELECT dataset_id, direction, count(*), sum(amount)
FROM qarzhy.cash_movements GROUP BY dataset_id, direction ORDER BY dataset_id, direction;
SELECT count(*) FROM qarzhy.documents;
SELECT count(*) FROM qarzhy.payment_plans;
SELECT count(*) FROM qarzhy.users;
```

## Что сохраняется

Все 954 операции и 30 планов SQLite включены по прямому подтверждению пользователя,
несмотря на исходную метку demo. Продажи и закупки создают документы и начисления,
оплаты — движения денег с распределением на подтверждённые документы. Расходы,
решения финансиста и их признание перенесены отдельно, без повторного признания.
Сессии исключены; пользователи входят заново со своими существующими паролями.

Excel переносится в денежные движения, справочники, товарные остатки,
задолженность поставщикам, кассовые остатки, группы активов и исторические
показатели P&L, бюджетов и продаж. Контрольные своды продаж/денег сохраняются
как отдельные исторические серии, не создают повторные денежные движения.
Нет связи с документом, организацией или складом, если её нельзя подтвердить.

## Почему импорт ещё требует сверки

SQLite хранится в `legacy_ledger`, Excel — в `imported_finance`. Оба набора реальные,
но перекрываются по датам и не должны автоматически складываться.
Правила `coverage_rules` не создаются до подтверждения границ отчётов.

Начальный остаток остаётся `draft`: исходные сводные и товарные суммы расходятся.
Есть даты, не совпадающие с годом/месяцем строки, пустые суммы кассовых остатков,
неизвестные счета и организации, строки без названия, вспомогательные листы
без достаточного контекста. Они перечислены в отчёте и `import_issues`.
Неподтверждённые вспомогательные значения остаются в архиве источника или
диагностике; это явно **не завершённый перенос всех исходных областей**.

Ошибки формул Excel сохраняются как `not_available`, пропуски — как `missing`,
а не нули. Отрицательные денежные суммы преобразуются в противоположное
направление с исходной суммой в диагностике.
Пока открыты вопросы источника, пакет остаётся `running`, `finished_at` пустой.
Не переводите его вручную в completed без сверки.

Этот SQL загружает данные; переход серверной части программы на новые таблицы
и расчёты отчётов — отдельная работа. До этого сайт использует прежнее хранилище.

## Проверка без подключения к рабочей базе

```sh
python3 -m unittest discover -s tests -p '*_test.py'
PGLITE_MODULE=/absolute/path/node_modules/@electric-sql/pglite/dist/index.js node scripts/verify_relational_export.mjs
```

Проверка использует временную PostgreSQL WASM: DDL, весь SQL, количество строк,
точные денежные суммы, признание расходов, отказ на непустой схеме и при
повторном запуске. Это не проверка на вашем сервере PostgreSQL и не сверка
с неподтверждёнными исходными остатками.
