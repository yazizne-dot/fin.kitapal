# Next.js to Node API cutover contract

The Next.js UI uses one catch-all `/api/[...path]` handler and forwards every API request to the standalone Node process named by `API_INTERNAL_URL`. Without that setting, the route returns HTTP 503. The old SQLite handler is no longer on the Next.js runtime path. A browser test verifies login and report navigation against the Node API and isolated PostgreSQL; the remaining data-fidelity gaps below still prevent claiming a full production cutover.

| Existing UI action | Current request | Node/PostgreSQL state | Work needed before cutover |
| --- | --- | --- | --- |
| Sign in, identity, password, logout, profile, users | `/api/login`, `/api/me`, `/api/password`, `/api/logout`, `/api/profile`, `/api/users` | Implemented with PostgreSQL sessions, CSRF and 30-day password rotation. The browser test covers finance login, mandatory admin password change and session rotation, and employee access isolation. | Verify real users' first sign-in with their own credentials and recovery procedures |
| Monthly finance workbook | `GET /api/data?source=auto|workbook&month=...` | Implemented for a covered P&L month, with partial balance/cash-flow projections | Configure coverage, verify openings and reconcile displayed values |
| Year-to-date workbook | `GET /api/data?range=ytd` | Sums covered monthly P&L through the latest actual month at or before the selection; reports missing coverage and flags a source `source_ytd` discrepancy when its revenue and cost identify the same cutoff | Verify YTD screens in a browser; budget and channel YTD totals need their own verified coverage |
| Organization and legacy ledger view | `GET /api/data?source=ledger&org=...` | Read-only `LedgerData` projection is implemented from imported events, movements, settlements, plans, periods and audit; organization access is scoped | Reconcile the browser view and restore source metadata lost in the original import before claiming full fidelity |

| Legacy correction form | `POST /api/correction` | Live non-cash portal operations reverse their posted fact and create a replacement in one transaction; original document amounts and cash movements are not edited | Imported operations remain unavailable for correction until their missing source metadata is restored; verify the unchanged modal in a browser |
| Legacy CSV import | `POST /api/import` | Uses the live operation adapter with per-row rollback, duplicate counts, row errors and one audited transaction; cash kinds reject until account selection exists | Verify browser CSV flow and add account choice for cash rows |
| Legacy budget form | `POST /api/budget` | Compatibility adapter stores the five legacy plan metrics in one organization/year draft, audits changes, checks scope and closed periods; the ledger view reads that draft | Verify the unchanged modal in a browser; decide when drafts are approved for the separate finance workbook |

| Report-number editor | `/api/finance/editor`, `/api/finance/cell` | Implemented against PostgreSQL override/history rows | Compare modal behavior and calculated totals with existing UI |

The restored `fin` database has only consolidated historical report series. It cannot supply organization or sales-channel history by guessing from metric labels. The 2026 source-YTD P&L total matches the sum of nonzero January–August monthly revenue within imported precision, but a source-YTD row is a separate stored value and does not identify an arbitrary selected cutoff month. The UI's YTD control must use the chosen month's covered monthly intervals unless a separately verified source total applies.

The Node API and Next.js request path have no SQLite dependency. Legacy SQLite modules and tests remain in the repository only as historical migration references. The applied PostgreSQL migrations and the approved January–August 2026 P&L coverage rule are documented in `fin-preflight-2026-10-22.md`.

The ledger projection groups imported `sqlite/operation/<id>` event and cash rows into one operation and refuses unknown cash classifications. All 954 imported operations in the restored database classify and the September 2026 closing balance reconciles. The original relational import did not preserve `external_id`, `source`, `point`, `document` or `due` for every event-only operation. The projection displays a stable generated external ID and source reference where a document is unavailable; only documented source metadata is reused. Restore these fields into PostgreSQL before relying on full legacy row detail or enabling corrections by original external ID. The imported tax-payment article is recognized by its exact confirmed label `Салық төлемі`; changing that label without an explicit type mapping will make the projection unavailable rather than silently misclassifying payments.

New non-cash operations use migration `0005_portal_operations` to preserve the old form fields and link them to posted live facts. Migrations `0003`–`0005` were applied to restored `fin` on 2026-10-22 and verified by read-only preflight. The ledger calculates depreciation under its existing rules; the separate live P&L currently has no verified depreciation metric mapping, so its net profit remains unavailable for a month containing a depreciation event rather than silently omitting that expense.
