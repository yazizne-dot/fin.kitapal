# Node.js API for the PostgreSQL finance portal

Date: 2026-10-21. Status: approved by the user. Target database: `fin`, schema `qarzhy`.

## Goal and boundaries

Replace the application's SQLite and runtime Excel/JSON readers with a separate Node.js API backed only by the already populated PostgreSQL schema. Keep Next.js as the browser interface and preserve the appearance and main workflows of every current portal page. The existing relational schema and imported data are the starting point; the API does not rerun the SQLite migration or restore a dump. PostgreSQL contains both the former SQLite ledger (`legacy_ledger`) and imported finance history (`imported_finance`). They are separate data sets inside one database and must not be summed merely because dates overlap.

The current routes and response shapes are a compatibility target, not a mandate to reproduce old SQLite tables or Excel cell storage. Any changed label or control must retain the page's layout and explain the PostgreSQL concept it edits. Scope includes login/account management, users and permissions, documents and operations, expenses and approvals, plans/budgets, reports, imports, audit, export, and the report-number editor. No second authentication factor is part of this release.

## Process and interfaces

- Run a separate Node.js HTTP API process. It binds to loopback by default. Next.js continues to serve pages and forwards same-origin `/api/*` requests and responses, including cookies and file downloads, to this process. The browser does not need a public API origin or CORS.
- Use a PostgreSQL connection pool configured through local environment variables. API startup verifies connectivity and the expected `schema_migrations` version; it does not create or reset the finance schema. Database credentials never enter the browser bundle or repository.
- Divide backend code into transport/validation, authentication/authorization, repositories, and bounded finance services: documents and settlements, cash, expenses, planning, reports and coverage, report corrections, and audit. Services own transactions and expose functions independent of HTTP request objects. Repositories use parameterized SQL and explicit `qarzhy` names.
- Preserve `/api/login`, `/api/logout`, `/api/me`, `/api/data`, and existing management paths while adapting their payloads to the new model. Keep a documented mapping from each existing UI call to its new service and PostgreSQL entities. Unsupported or incomplete report data is represented explicitly rather than fabricated.

## Authentication and authorization

- Verify existing salted password hashes in `qarzhy.users`. On login, create a cryptographically random opaque session token. Store only its SHA-256 hash in `qarzhy.sessions`; deliver the token in a host-only `HttpOnly; SameSite=Strict` cookie, with `Secure` on HTTPS. Do not put tokens in local storage, URLs, logs, or API JSON.
- For each protected request, resolve the hashed token, expiry, active user, role, and explicit permissions from PostgreSQL. Apply authorization to reads and writes and constrain employees to their own expenses regardless of supplied IDs. Revoking an account or changing its role invalidates its sessions. Logout and password change invalidate prior sessions. Preserve a normal session maximum of 24 hours and a 30-day maximum for the existing remember-me control; neither bypasses password expiry.
- Require a password change every 30 days for every role, including admin. Add `password_changed_at` by an additive migration. Existing imported accounts have an unknown last-change date, so require a change at their first login after cutover; do not guess a historical timestamp. When password change is due, grant a restricted session that can access only account identity, password change, and logout. The password-change endpoint verifies the current password, checks the new password against a weak-password blocklist, updates the salt/hash and timestamp transactionally, clears `must_change_password`, revokes other sessions, rotates the current token, and audits the action. New passwords must be at least 15 characters; do not impose character-class rules. Admin resets issue a temporary password with `must_change_password` and revoke sessions.
- Check `Origin` against the configured public Next.js origin and inspect fetch metadata on state-changing browser requests, including login; the API's private loopback host is not the browser origin. Require a session-bound CSRF token in a header for authenticated mutations. Limit login and password-change attempts with PostgreSQL-backed counters shared by all API processes. Keep login errors generic. Log security events without credentials or tokens. Restrict database privileges of the API role; schema changes use a separate migration role.

## Finance writes and reports

- New records use the `live` dataset. Posting a document, settlement, expense recognition, or cash movement runs in one database transaction, checks permission and period closure, uses an idempotency key or version where appropriate, and writes an audit record. A repeated request cannot post the same financial fact twice. Corrections to posted facts use reversal/replacement according to the relational model rather than overwriting imported history.
- The existing source selector maps to distinct PostgreSQL data sets: historical finance and the former ledger. The selector's labels may be clarified, but both views come from PostgreSQL. The normal combined report selects historical values or live events through `coverage_rules` for each report family, scope, metric, and period. Different families may have different cutover dates. No implicit addition of `legacy_ledger` to `imported_finance` is allowed.
- Add a one-time coverage setup in the existing settings area for finance/admin users. It records and validates cutover ranges per report family and scope. Balance reporting requires a verified opening snapshot at the rule's starting date, as already enforced by the schema. Until a rule or verified snapshot exists, show available historical information and a clear incomplete-coverage warning; do not present an invented combined total. Once configured, new live facts automatically enter the selected report periods. A changed coverage rule is audited.
- Keep the report-number editor's visual layout and its ability to edit individual figures. Add a keyed report-override table for data set, report family, scope, period and period kind, metric and optional article/channel dimension, plus an append-only change history. This is needed because existing `financial_adjustments` can point to particular source records but cannot represent every computed report figure. Each edit requires a reason and author, records the original and replacement amount, checks the displayed revision, and permits reset. Edits affect the report calculation graph, not documents, `financial_events`, or `cash_movements`. Dependents such as gross profit and net profit recalculate. If a user explicitly overrides both an input and a derived total, the explicit total wins for that node and downstream calculations use it; the interface marks the resulting reconciliation difference. Imported historical values remain traceable to their original records.
- Use decimal arithmetic for money and preserve availability states (`reported`, `missing`, `not_available`). Do not convert missing values to zero. Show gaps and source discrepancies in the checks view. Exports must reflect the same effective report numbers and access scope as the screen.

## Errors and validation

Validate request bodies, IDs, amounts, dates, pagination, report filters, and revisions at the API boundary. Return consistent JSON errors with the existing frontend's `error` field; use 401 for missing/expired sessions, 403 for forbidden actions, 409 for version or idempotency conflicts, 422 for invalid business data, and 503 for unavailable PostgreSQL. Never expose SQL details. No user-specific API response may be cached. Unexpected failures are logged with a request ID; audit records describe accepted business changes, not failed partial transactions.
