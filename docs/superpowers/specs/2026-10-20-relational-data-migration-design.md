# Перенос данных в реляционную схему

Источники проверены 20.10.2026. Рабочая PostgreSQL не изменялась.

## Источники и назначение

- `data/workbook-source.json`: P&L и бюджетирование. Перенос в historical_series/historical_values с разделением месяцев, исходных годовых итогов и плановых показателей. Без вымышленных документов продаж.
- `data/cashflow-source.json`: лист База — первичные денежные строки; остальные листы преимущественно контрольные своды. Перенос в cash_movements и справочники; своды не создают повторные движения.
- `data/balance-source.json`: товары, издательства, договорные условия, количество и стоимость остатков, касса и основные средства. Перенос в справочники и таблицы остатков. Заголовок листа Баланс — 01.09.2026; даты остальных областей проверить отдельно.
- `data/portal.sqlite`: 954 операции, 30 планов, 12 пользователей, 4 расхода, 4 финансовые записи, 42 записи аудита. Происхождение финансового журнала требует подтверждения; архитектура выделяет legacy_ledger. Сессии не переносятся.

## Преобразование

Читать JSON через Decimal, SQLite в read-only snapshot с учётом WAL.
Присваивать стабильные ключи и ID; не объединять сущности только по имени.
Повторный fingerprint не должен создавать дубликаты.

В База Cash Flow: C — дата Excel, D/E — приход/расход, F/I — ответственный/автор,
G — статья, H — примечание. Проверять дату по A/B (год/месяц).
Два ненулевых направления дают две записи. Организацию и счёт не угадывать.

Технические повторения, заголовки и формулы не становятся финансовыми фактами.
Каждую исходную область классифицировать в локальном отчёте. Неопознанные
значимые строки и несогласованные суммы блокируют завершение импорта.
Исправления SQLite применять только при проверенном соответствии исходнику.

## Результат и проверка

Новый SQL данных для уже созданной реляционной схемы, локальный отчёт количества
записей, сумм прихода/расхода, остатков и исторических показателей.
Проверить импорт на временной PostgreSQL, внешние ключи, повторный запуск,
откат при ошибках и отсутствие двойного учёта. Пароли не выводить в отчёт.

## Подтверждённое решение

Пользователь подтвердил: все 954 операции и 30 планов SQLite переносить как
реальные, несмотря на исходную метку demo. Метка остаётся в отчёте происхождения.
Данные сохраняются в отдельном dataset legacy_ledger; это реальные записи,
а не основание автоматически складывать их с пересекающимися сводами Excel.
