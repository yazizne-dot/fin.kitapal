# Разовая настройка роли основной fin

Проверено 27.10.2026: `qarzhy_app` отсутствует. Текущая `fin_user` не имеет CREATEROLE; её права не меняются. Фактический адрес подключения на этом компьютере — `127.0.0.1:15433`, база `fin`, через существующий SSH-туннель.

Штатный `scripts/provision-local-app-role.mjs` ожидает порт **5436**, поэтому для этой базы не запускается и не изменяется.

Точные команды PostgreSQL находятся в [provision-main-fin-app-role.sql](sql/provision-main-fin-app-role.sql). SQL выполняется одной транзакцией, проверяет имя базы, отпечаток импорта, пять миграций и отсутствие роли. Пароль роли передаётся параметром через локальную настройку транзакции, а не сохраняется в SQL.

Права новой роли:

- LOGIN, без SUPERUSER, CREATEDB, CREATEROLE, REPLICATION и BYPASSRLS.
- CONNECT к fin и USAGE схемы qarzhy; без CREATE и владения объектами.
- SELECT только на явно перечисленные таблицы backend и preflight.
- INSERT/UPDATE только на перечисленные рабочие таблицы; DELETE только для sessions, login_attempts и report_overrides.
- USAGE только identity-последовательностей таблиц с разрешённым INSERT. Автоматических прав на будущие таблицы нет.
- UPDATE на financial_articles и coverage_rules необходим также для блокировок SHARE ROW EXCLUSIVE в их триггерах. Исходный provision-скрипт не учитывает эти два разрешения.
- Таймаут запроса 30 секунд, простаивающей транзакции 15 секунд.

## Выполнение на этом компьютере

Подготовлен игнорируемый локальный исполнитель `.env.provision-app-role.mjs`. Он использует тот же проверенный TLS-сертификат, что и backend, и жёстко проверяет **15433/fin**, включая совпадение адреса с `.env.backend.local`.

Временный `.env.pg-admin.local` нужен только этому исполнителю: в нём административные реквизиты для создания роли и выдачи GRANT. Backend этот файл не читает. Администратору необходимы CREATEROLE и полномочия выдавать перечисленные права; обычно используется владелец/администратор PostgreSQL. Давать CREATEROLE пользователю fin_user не нужно.

После заполнения PGUSER и PGPASSWORD в этом локальном файле:

```sh
node .env.provision-app-role.mjs --check
node .env.provision-app-role.mjs --apply
```

`--check` только проверяет подключение и наличие роли. `--apply` использует уже сгенерированный пароль приложения из `.env.backend.local`, создаёт роль и выдаёт права одной транзакцией. При существующей роли останавливается, не меняя пароль.

После COMMIT выполняется отдельный вход как qarzhy_app, проверяются TLS, пять миграций, разрешённые/запрещённые права и чтение документов/денежных движений. Только после успешной проверки `.env.pg-admin.local` удаляется. При ошибке до COMMIT транзакция откатывается; после COMMIT исполнитель сообщает, что роль уже создана, и не пытается автоматически пересоздать её.

Пароль администратора используется только в памяти процесса для подключения; не передаётся аргументом команды, не включается в SQL, не выводится в журнал. Все локальные файлы с реквизитами игнорируются Git и имеют режим 600. В основной процесс API передаётся только DATABASE_URL отдельной роли.
